## Header
Goal: the effective `output_language` setting actually changes what the system WRITES, so a newly generated PRD, memo or plan body comes out in the chosen language while every machine-read surface, and this repo's own artifacts, stay English.

Serves: PRD-001's outcome, "a non-English PM/builder runs the full Odeo lifecycle and every artifact they read is in their chosen language, after a single setup choice, while the codebase, tooling and collaboration stay language-neutral." This story is the payoff story: USR-002/003/004 shipped the setting, the resolver and the change command, and until this story the setting changed nothing a user reads. It covers PRD-001 R2 (localized surfaces), R3 (English-always surfaces) and R4 (the public Odeo repo stays English). It does NOT cover R7 (the mismatch warning), which is USR-006.

Architecture context (inherited, not redecided):
- Deterministic logic lives in `bin/*.sh` with self-contained `tests/*.test.sh`; style `set -uo pipefail`, exit 0 clean / 1 violation / 2 usage error, `mktemp` fixtures. Instruction surfaces are markdown: `skills/<name>/SKILL.md`, `agents/<name>.md`, `AGENTS.md`, `global/CLAUDE.md`.
- The setting is ONE line, `output_language: <code>`, code in `en de hr fr`. Precedence project > global > `en`, implemented by `bin/resolve-language.sh` (USR-002, shipped). `bin/language-status.sh` adds the scope (USR-004, shipped). `/language` shows and changes it (USR-004, shipped). Both scripts read the global config from `CLAUDE_GLOBAL_CONFIG` with `$HOME/.claude/CLAUDE.md` as the default (`resolve-language.sh:37`, `language-status.sh:42`), which is what makes hermetic tests possible and what makes an unprefixed test call non-hermetic.
- The no-leak gate is `bin/language-guard.sh` (USR-001, shipped, 19 cases). It is STANDALONE: nothing invokes it automatically, and it never reads prose below the frontmatter's closing `---`.
- Guardrails are tagged `[E]` enforced / `[I]` instructed, and AGENTS.md is their single source of truth: skills and agents REFERENCE them, never restate them. Safety-critical rules are additionally embedded in agent/skill bodies because those files ship to the user's machine and `AGENTS.md` does not (verified: `install.sh` copies `project-templates/`, `skills/`, `agents/`, `docs/*.md`, `docs/checklists/*.md`, `bin/*.sh` and `global/CLAUDE.md`; it never copies `AGENTS.md`).
- Mechanical invariants over the system's own files live in `docs/invariants.md` + `bin/skills-lint.sh` + `tests/skills-lint.test.sh`, maintained in the order doc -> RED -> GREEN.
- Dev rigor for this repo: TDD-lite, plus the house rule "coverage claims are proven by mutation, not asserted" (`CLAUDE.md`). Prose files have no unit test; they are covered by `skills-lint`, by the deterministic assertions in Task 5, and by reviewers.

## Design decisions (resolved, so the builder does not guess)

1. **AGENTS.md gets a new numbered guardrail section, `### 7. Output language`, not a prose paragraph elsewhere.** Reason: this story's rules split into genuinely enforced and genuinely instructed halves, and the `[E]`/`[I]` tagging convention plus "a rule that is not written here does not exist" both live in the Guardrails section. A side effect worth having: USR-001's `[E]` no-leak gate is currently absent from AGENTS.md entirely, so the guardrail list does not today mention the mechanism AC2 and AC4 depend on. This section closes that gap in the same edit.

2. **The whole frontmatter block stays English, not just field names and enum values, and the LOCALIZED title lives in the document's H1 instead.** `bin/language-guard.sh:133-137` applies the ASCII rule to EVERY top-level frontmatter VALUE, so a localized `title: Anmeldung mit Zeitueberschreitung` survives only while it stays ASCII, and a title carrying an umlaut FAILS the `[E]` gate. A rule that permitted localized frontmatter would therefore contradict the gate that enforces it. Decision: localization begins after the frontmatter's closing `---`, which is exactly the boundary USR-001 designed ("Prose body text is never read"). Because `title:` is the single most-read piece of prose in a PRD or a story, the English `title:` is paired with a REQUIREMENT rather than left as a loss: the document's H1, which by this repo's own convention repeats the title below the frontmatter (`docs/prds/PRD-001-output-language.md:3` `title: Output language option` and `:8` `# PRD-001: Output language option`), carries the localized title. The H1 sits below the closing `---` and is therefore out of the guard's reach by design, so the reader gets a German title on the line they actually read while the machine-parsed field stays ASCII. The ID prefix in the H1 (`PRD-901:`) is an identifier and stays as it is. This is one step stricter than AC2's literal words (field names + enum values); it is recorded in Risks for the human to strike at the gate.

3. **A heading or label that appears as a LITERAL in a format doc, a skill's document shape, or an agent's output template stays English; anything the writer composes freshly is localized.** That is the bright line, stated as a rule rather than as a list, and the list is its consequence: frontmatter keys, `docs/plan-format.md`'s field names and section headings, eval-record fields, the `## Verdict` / `## Scores` output headings in the reviewer agents, the PRD's eight section headings and the story card's field names, AND the inline field labels inside an agent's output template, specifically `**What:**`, `**Why it matters:**` and `**Example scenario:**` (`agents/architecture-reviewer.md:95-97`). Inline field labels are named explicitly because they are the case the general phrase "format spec" does NOT reach: they are defined by an AGENT's output format, not by a format document, so without naming them two reviewers would legitimately diverge (`**What:**` in one, `**Was:**` in the other). Neither spelling breaks a gate; both break a human's grep across `docs/evals/`. Reason for the whole rule: those labels are the anchors other agents and humans locate (spec-gate, the builder, the reviewers, `merge-gate`, grep); localizing an anchor breaks the reader, not the writer. PRD-001 R2 asks for "bodies" and "prose", which this satisfies. Alternative considered and rejected for now: localize headings for human-only documents (PRD, memo, research) and keep them English for contract documents (plans, stories, eval records). Rejected as a second rule class with a fuzzy border, for a story whose whole difficulty is that prose has no compiler. Reversible later per artifact type; recorded in Risks.

4. **The effective language reaches an agent that has no `Bash` by being handed to it at dispatch (Contract C1), never by that agent inventing it.** `architect`, `architecture-reviewer`, `design-reviewer`, `pm-reviewer`, `skill-reviewer` and `agent-reviewer` hold no `Bash`, so they cannot run `resolve-language.sh`. The system already has exactly this pattern and it is already a guardrail: "Whoever dispatches a reviewer supplies the commit sha, because only `code-reviewer` holds `Bash`" (AGENTS.md Guardrails 1). USR-005 reuses that shape rather than inventing a mechanism, which is also why this story needs no ADR. The fallback chain is NOT restated here: it is declared once in C1 and every other surface points at it, so editing one cannot leave the other stale. Two properties of the mechanism, which C1 also carries: never ask the user mid-run, and never guess a language from the input document's language.

5. **The language is a property of the TARGET PROJECT, not of the current working directory.** This matters concretely: the live check in Task 6 runs from this repo (whose own override is `en`) while planning for a fixture project set to `de`. Hence the handed line outranks anything the agent infers from its own surroundings, and C1 says so.

6. **The enforced wiring list is a FLOOR, and it is mechanically checked (new lint invariant C13), not left to convention.** The universal rule in AGENTS.md is `[I]` and covers all 66 skills. C13 additionally requires, in the files where a miss is most expensive, BOTH the literal token `output_language` AND a pointer to the canonical rule (the literal `Guardrails 7`): the five skills that save a prose document (`prd`, `stories`, `critique`, `research`, `product-signal`), `skills/build/SKILL.md` (the dispatcher that must hand the value over), and EVERY agent definition (detected exactly as C12 detects one). The pointer half exists because a marker alone cannot tell a POINTER from a RESTATEMENT: with only the token, someone can rewrite a bullet into a full local copy of the guardrail and the lint stays green forever. Two greps in one loop close that. Reason for "every agent definition" instead of a hand-picked subset: any other line is arbitrary, and `agents/` is small and stable. Reason for a lint at all: the repo's own convention is that a bug class a grep could catch gets a grep (`docs/invariants.md`), and the failure mode here is silent (a new prose skill ships with no wiring and every gate stays green).

7. **`language-guard.sh` needs NO code change for AC2, and stays untouched.** Read line by line, it already covers: filenames (`check_filename`, ASCII + `^[A-Za-z0-9._-]+$` + slug tail after date/ID-prefix stripping), directory names, frontmatter field names (`^[a-z0-9_-]+$`), the one closed enum `model_tier` (`fast strong strongest`), all other frontmatter values (ASCII), branch names (via `--branch`), and conventional-commit type (closed English allowlist of eight) plus scope (ASCII + `^[a-z0-9-]+$`). What is MISSING is not a check but an INVOCATION over an artifact of the shape this story produces, plus honest wording about the three things the guard cannot see: whether an ASCII word is English (`feat(anmeldung)` and `PRD-907-anmeldung.md` both pass), code and identifiers (never inspected), and indented frontmatter children (deliberately skipped, USR-001 arch-review BLOCKING-1). Task 5 adds the invocation; Task 1 adds the honest `[E]`/`[I]` split. Touching the guard would re-stale USR-001's 19 cases for no gain.

8. **`verdict:` values get named explicitly, because the guard deliberately does not close-list them.** `language-guard.sh:30-33` leaves `verdict`/`status` free text (USR-001 arch-review BLOCKING-2, so the guard never out-stricts the gates). The real net is `bin/merge-gate.sh:206-218`, which accepts only `APPROVE | APPROVE WITH COMMENTS | PASS` after uppercasing: a localized verdict REFUSES the merge. So "never localize a verdict" is `[I]` with a fail-closed `[E]` backstop, and the rule says exactly that rather than implying the guard catches it.

9. **AC1 is verified in two layers, the plan says out loud which layer proves what, AND what a layer-2 FAIL costs.** Layer 1, deterministic and enforced: the wiring exists at every listed surface (`skills-lint` C13) and the resolver returns the fixture's language (`tests/localized-prose.test.sh`). That proves the CAUSE is in place, not the EFFECT. Layer 2, live: a named procedure (`docs/checklists/language-live-check.md`) that dispatches a fresh `architect` against a German fixture project and has a human read the returned plan. There is no compiler for prose and the detector is USR-006, so no script in this repo can assert "this body is German". The `builder` agent holds no `Task` tool, so it CANNOT run layer 2: the live run belongs to the orchestrating session at gate B6, and the builder must report AC1 as "wiring proven, live check pending at the gate", never as passed. Consequence of a layer-2 FAIL, decided here so nobody improvises it at the gate: an AC1 fail is a fail of the WORDING shipped in Tasks 1 to 3, so the remedy is a wording revision plus a fresh dispatch, never a re-run of the same configuration hoping for a different sample. And the merge WAITS: gate B6 sits after `code-reviewer` has already approved, and `merge-gate.sh` reads only the reviewer verdict, so nothing mechanical refuses a merge on an AC1 fail. The human at the gate is the only stop, which is exactly why the Success signal row and the checklist both say it. This follows `knowledge/evals/environment-claims-need-behavioral-tests.md`: an instruction's behavior is only testable by running it, and form review must never stand in for a measurement.

10. **The fixture story used by the live check is written in ENGLISH on purpose.** If the input story were German, a German plan would prove mimicry, not obedience to the setting. Same knowledge entry, guidance 5 (do not let the scenario suppress or confound the step under test).

11. **`global/CLAUDE.md` gets the rule as one bullet, and must NOT get an `output_language:` line.** It is the only vehicle that reaches an installed user's global config (`install.sh:113`), so the rule has to be there for the feature to work outside this repo. But a tracked `output_language:` line in that file would be copied to `~/.claude/CLAUDE.md` at install, `set-global-language.sh` would then see a line already present, and USR-003's one-time question would never be asked. That trap is named in the File map as a NO CHANGE OF THIS KIND entry.

12. **The question that ESTABLISHES the setting is English by construction, and rule C says so.** Rule C localizes chat replies, which would otherwise collide with `skills/setup-project/SKILL.md:157-164` (step I2) and with `install.sh`'s one-time global-language prompt (USR-003): both ASK which language to use, before any setting exists to follow. One clause resolves it: the setup question and the install prompt are English because no setting exists yet at the moment they run. Everything after the answer follows the setting.

13. **A crude non-English FLOOR is DECLINED as a pass/fail criterion, and taken only as a recorded, non-deciding diagnostic.** The option considered: assert that the live-run body contains non-ASCII letters above a threshold, or German stopwords above a threshold, so that "no script can say anything" becomes "a script can say it is not English". Declined as an assertion for three reasons, all cheap to check and all fatal to it as a gate. (a) It is not sound in either direction: correct German prose can be entirely ASCII (a whole German paragraph legitimately can carry no umlaut), while correct English prose can carry non-ASCII (a quoted German filename, a cited name, an accented letter inside an example). A gate with false positives AND false negatives on the story's headline criterion is worse than an honest "the human reads it", because it invites building to the gate. (b) The stopword variant IS a German detector by construction, which is the thing it must not become and the thing USR-006 owns; adding it here would fork the detector across two stories. (c) It would put a script's word next to a human's read on the same row, and when they disagreed nobody would know which one the story is closed on. What IS taken: the live checklist records a diagnostic count of non-ASCII letters in the saved sample, labelled explicitly as a hint that decides nothing, so a reviewer reading the gate report later can see the number without it ever being the criterion. The real answer to "make AC1 script-closable" is USR-006's detector, and Risk 1 says so.

## Contracts (declared once, referenced by name)

### C1: the dispatch language line
- Kind: prompt-field convention (text handed to a dispatched agent) + the receiving agent's fallback chain
- Declaration: whoever dispatches an agent that will write prose includes in the dispatch prompt one line of the exact form `output_language: <code>`, where `<code>` is the stdout of `resolve-language.sh <target-project-dir>` (the script is in `~/bin` or `bin/`). The receiving agent writes its PROSE in that language and applies it to nothing else. If the line is absent, the agent reads the first `^output_language:` line of `<target-project-dir>/CLAUDE.md`; if that is absent too, it writes English AND states in its result that no output language was supplied. The handed line outranks anything the agent infers from its own working directory (design decision 5). The agent never asks the user mid-run and never infers a language from the input document.
- Produced by: Task 1
- Consumed by: Task 2, Task 3, Task 6
- Invariants: the code is always one of `en de hr fr` (the resolver's closed set, USR-002); the line never carries a language NAME, only a code; a missing line degrades to English and is DISCLOSED, never silently guessed, and the disclosure carries the literal fragment `no output language was supplied`, which is the character-exact AGREEMENT MARKER of this contract: the identical fragment appears in C1's Declaration above, in Task 3's Implement bullet spec and in Task 3's Verify grep, and it is paraphrased at none of them, so the ten-file agreement check tests obedience to this contract rather than to a restatement of it (a builder who writes the ten bullets from C1 passes that check by construction); the line is handed over on EVERY dispatch of an agent, including every re-dispatch inside a review loop, for the same reason the commit sha is (a loop regenerates the record, so a later round would otherwise drop it).

## Risks / open questions
1. **AC1 is not closable by a script, and this plan does not pretend otherwise.** The story's own note asks for "generating a sample artifact under a German setting", which is a live run. The residual risk is a green suite reading as a passed story: the mitigation is that the Success signal row says so, names what a fail costs, and `docs/checklists/language-live-check.md` names who runs the live step, while the builder is instructed to report AC1 as pending at the gate. The cheap non-English FLOOR that would convert "no script can say anything" into "a script can say it is not English" was considered and DECLINED as a criterion (design decision 13): it is unsound in both directions (German prose can be all-ASCII, English prose can carry non-ASCII), and its stopword variant is a German detector by construction, which is USR-006's scope and must not be forked here. It survives only as a recorded, non-deciding diagnostic. If the human wants AC1 script-closable, that is USR-006 and the two stories should be built together; ASK rather than deciding it mid-build.
2. **Two rules go one step beyond AC2's literal words, deliberately.** (a) The WHOLE frontmatter block stays English, not only field names and enum values, because `language-guard.sh` ASCII-checks every value and a localized `title:` with an umlaut would fail the `[E]` gate (design decision 2). The cost is named rather than hidden: `title:` is the most-read line in a PRD or story, so a German PM would get an English title. That is why the same decision REQUIRES the localized title in the document's H1, below the closing `---` and out of the guard's reach by design, which is where the repo's own documents already repeat the title. If the human prefers the reverse (localized `title:` plus a relaxed guard), that is a USR-001 change and an ADR, not a plan detail. (b) Commit messages stay English in full, subject included, because git history is a shared collaboration surface; PRD-001 R3 names only type and scope, and the AGENTS.md bullet says "beyond PRD-001 R3, decided in USR-005" so a later reader can tell a decision from a drift. Both are conservative and both are one-line strikes at the gate if the human disagrees. Neither affects this repo, whose override is `en`.
3. **Structural labels stay English (design decision 3), so a German PRD keeps English section headings and English inline field labels.** A user might reasonably want localized headings for human-only documents. Two sub-cases are worth the human's eye: the section headings of a PRD or memo, and the inline field labels inside an agent's output template (`**What:**`, `**Why it matters:**`, `**Example scenario:**`), which no gate reads at all, so the only cost of localizing them would be a broken grep across `docs/evals/` and the only cost of keeping them English is a German reviewer's finding wearing English labels.
