# PRD-002 eval: Odeo as a PM plugin that ends with a delivery-ready package (v4)

## Scores

- Problem clarity: 2. Who hurts, how much, why now, each sourced or tagged. The
  maintainer's pain is measured and dated: "Measured on 2026-10-22/23 in this repository:
  41 of the last 100 commits were review records of delivery work ... 7 of the 10 agents
  (75% of agent text) and 16 of the 67 skills (33% of skill text) serve delivery". The
  audience pain is tagged: "Assumption, not yet validated with users". Why now is sourced:
  "repository `ivansolic/Odeo`, read 2026-10-23: 1 star, 0 forks, 25 unique cloners in 14
  days". The v3 comment is addressed in section 3: "Assumption, not measured: building is
  well served elsewhere". Checked in the tree at 2773575: 67 skills and 10 agents exist,
  and the 16 named skills in scope item 2 are 16 distinct existing skills, so those counts
  hold; commit, token and GitHub figures cannot be re-checked here and are scored as
  written (dated, sourced). Comment, not a deduction: section 1 still states the same
  premise untagged, "building is already well served by dedicated development tools".

- Measurable outcome: 2. User outcome: "a founder, entrepreneur or PM takes a fuzzy idea
  through Odeo to a package that is ready for delivery: whoever builds it ... can start
  without asking anything the package already decides." Metric and target: "in 3 of 3
  pilot handoffs, the builder's first questions are only about things the package leaves
  open ... Measured by reading each pilot transcript or conversation against the package",
  plus "review-record commits are under 15% of all commits (41% before), measured with
  `git log`." Comments unchanged from v3: no named reader for the pilot transcripts and no
  time box for the pilot. The core path (scope item 7) has no metric of its own; that is
  one of the two critique findings the maintainer declined, the rubric does not require it,
  and it is not scored.

- Scope discipline: 1. All three v3 edges are closed: `spec-gate` and `coverage-check`
  now stay, "because the package needs both (decided 2026-10-25)", and R1's AC uses both;
  the archive and repository-only copies agree ("The copy on a tagged archive branch is
  not maintained ... the maintainer's own merge gate and code-reviewer are kept and
  maintained separately as repository-only tooling (R6)"); public launch is now Out ("A
  public launch campaign or demo; whether and how to launch is decided after the pilot").
  v4 opens new edges where the added items meet the rest of the document:
  1. **In contradicts Out.** Out says "Removing or rewriting PM skills beyond the
     core-path ordering". Two new In items rewrite PM skills that stay. Item 9 / R13
     changes how `prototype` shares ("when sharing a prototype the user is asked how long
     it stays open ... the share can be extended while it is open and the people it was
     sent to keep the same link"). Item 8 / R12 ("no shipped agent, skill, rubric, record
     format, gate or instruction file mentions a model tier") requires editing remaining
     PM skills: in the tree at 2773575, `skills/setup-project/SKILL.md` lines 135-138 offer
     the "strongest" / "strong-default" model choice and `skills/start/SKILL.md` line 34
     checks the model preference. Likewise "Changing what the PM skills produce ...
     beyond what the package needs" sits next to R12 dropping `model_tier` from the record
     format pm-reviewer produces. The non-goal's single named exception does not cover
     either item, so a reader cannot tell from the document whether these rewrites are in.
  2. **The slice is no longer only thin.** Under "In (the thin slice)", item 9 (longer
     prototype shares) neither tests the outcome (a delivery-ready package) nor serves the
     cut; it is a separate improvement to a kept skill. The PRD records it as a maintainer
     decision, which explains it but does not tie it to the outcome.
  3. **Numbering breaks the cross-references.** The In list runs 1, 2, 7, 8, 9, 3, 4, 5, 6.
     Rendered Markdown renumbers an ordered list sequentially, so "the core path (scope
     item 7)" in section 7 displays as item 7 = "Instructions", and the core path displays
     as item 3. Only the raw file reads correctly.
  4. **An AC carries an open premise.** R13: "(whether today's re-run changes the link is
     to be verified first)". Honestly flagged, but the AC's own outcome depends on it; the
     current `prototype` skill says "extend by re-running" (line 50), and
     `scripts/share-tunnel.sh` waits for a new public URL from cloudflared on each run
     (line 38), which suggests (not verified by running it) that the link does change today.

- Risks & assumptions: 2. Riskiest assumption named and falsifiable: "H1 (riskiest): a
  package of PRD, stories and a short brief is enough to start building ... Wrong if: in a
  pilot a builder asks something the package should have answered, or misstates the
  scope." H2 to H4 each carry a "Wrong if". The two new critique risks carry detection:
  Weight, "Detect: sessions that produce one document and never a second step", with its
  mitigation tied to scope item 7; Reach, "Detect: repository traffic and installs stay
  near zero for 30 days after the release". Comments: Weight's detection has no window or
  threshold; H2 watches "within 60 days of the release" and Reach "30 days" for largely
  the same signal, and with launch now Out, H2's outside-signal test is weak by design,
  which the Reach risk openly acknowledges. The pilot-before-the-cut finding the maintainer
  declined is not required by the rubric and is not scored.

- Security & data: 2. Applies: the cut removes protections users had, the package can
  carry private data, and R13 lengthens public exposure. The pre-mortem is in the rubric's
  form ("It is six months later and a user leaked a secret through a project Odeo set up.
  What was the hole?") and now has seven answers, each captured as a requirement with a
  testable AC: R4 ("a new project's pre-commit refuses a planted secret"), R7 ("a planted
  e-mail address or key produces a warning the user must answer"), R8, R9 ("a pilot
  package built from an interview synthesis with planted names contains none"), R10 ("a
  push of it to the public remote is refused"), R11 (`share-tunnel.sh` and
  `second-opinion.sh` ship; both exist in the tree at 2773575 and are referenced by
  `prototype` and `second-opinion-pm`), and R13 ("every share still announces its end time
  and closes on its own, and `/odeo:start` lists shares that are still open"). Comments,
  not deductions: R13 sets a floor ("a duration of a full working day (8 hours) is
  accepted") but no ceiling on duration or on the number of extensions, so "always ends on
  its own" holds only in the trivial sense; and R10 requires a refused push while R4 says
  "the pre-push guard goes with the build half", without saying that the repository's own
  guard (R6 keeps the "publish guard") is what refuses it.
