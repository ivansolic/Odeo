# PRD-002 eval: Odeo as a PM plugin that ends with a delivery-ready package (v3)

## Scores

- Problem clarity: 2. Who hurts is named twice, each with a source or a tag. The
  maintainer's pain is measured and dated: "Measured on 2026-10-22/23 in this repository:
  41 of the last 100 commits were review records of delivery work; 72 code-reviewer runs in
  30 days ... 7 of the 10 agents (75% of agent text) and 16 of the 67 skills (33% of skill
  text) serve delivery". The audience pain is honestly tagged: "Assumption, not yet
  validated with users: this framing narrows the audience". Why now is sourced and dated:
  "repository `ivansolic/Odeo`, read 2026-10-23: 1 star, 0 forks, 25 unique cloners in 14
  days". Checked in the tree at 265e68c: 67 skills and 10 agents exist, so those two
  counts match; the commit, token and GitHub figures cannot be re-checked here and are
  scored as written (dated, sourced). Minor, not decisive: "building is already well
  served by dedicated development tools" (section 1 and section 3) is a premise of the cut
  that carries no source and no assumption tag; and "about 1.5M tokens each (13 runs of one
  session, about 20M tokens)" reads as a per-run average extrapolated from one session.

- Measurable outcome: 2. User outcome: "a founder, entrepreneur or PM takes a fuzzy idea
  through Odeo to a package that is ready for delivery: whoever builds it ... can start
  without asking anything the package already decides." Metric and target: "in 3 of 3
  pilot handoffs, the builder's first questions are only about things the package leaves
  open ... Measured by reading each pilot transcript or conversation against the package",
  with a diversity condition ("at least two different build setups ... at least one of the
  three ideas comes from a person who is not the maintainer"). Secondary: "review-record
  commits are under 15% of all commits (41% before), measured with `git log`." Comments,
  not deductions: the primary metric names no reader (the maintainer judging his own
  pilots is the obvious bias) and no time box for the pilot.

- Scope discipline: 1. The structure is right: a numbered "In (the thin slice)" list with
  decision dates, and an explicit "Out (non-goals)" list ("Building, recommending or
  integrating any build tool", "A Codex or other host port", "Migration tooling"). The
  edges are fuzzy in three places:
  1. The cut list labels PM-side machinery as build-only: "the build-only scripts
     (merge-gate, spec-gate, boundary-check, coverage-check, focus-check)". In the tree at
     265e68c, `skills/stories/SKILL.md` lines 68-71 make `coverage-check.sh` the "[E]
     enforced backstop" for the story set's PRD traceability map, a PM quality step, and
     lines 79 of the stories skill and 49 of the prd skill tie the review round to
     spec-gate. R2's AC ("no remaining skill ... points to one") forces those pointers out,
     while R3 promises "Nothing PM is lost". The PRD does not say whether the stories skill
     loses its deterministic coverage check or what replaces it, and R1's package step
     ("after the stories pass their review") does not take that job over.
  2. Scope item 2 says the cut items "go to a tagged archive branch ... and are not
     maintained", and its list includes merge-gate and code-reviewer; R6 says "The
     maintainer's own merge gate and code-reviewer move to a repository-only folder ...
     so they keep working on this repository". Two fates for the same two items; a reader
     can reconcile them (shipped copy archived, repo copy kept), but the document does
     not.
  3. Open question 2, "Audience of the first release: the maintainer's own work, or a
     public launch with positioning and a short demo?", leaves a possible deliverable (the
     demo) neither In nor Out. Open question 1 is acceptable: the pilot (scope item 5) is
     the declared way to answer it, and R1's AC already fixes the minimum content.

- Risks & assumptions: 2. Riskiest assumption named and falsifiable: "H1 (riskiest): a
  package of PRD, stories and a short brief is enough to start building ... Wrong if: in a
  pilot a builder asks something the package should have answered, or misstates the
  scope." H2 to H4 each carry a "Wrong if". Section 7 adds value, usability and
  feasibility risks with detection ("Detect: H3, the second build setup in the pilot").
  Comment: H2's signal ("within 60 days of the release nobody outside the maintainer opens
  an issue, stars or installs it") only works for a public release, which open question 2
  has not decided.

- Security & data: 2. Applies: the cut removes git protections users had, and the package
  can carry private data. A pre-mortem is written in the rubric's form: "It is six months
  later and a user leaked a secret through a project Odeo set up. What was the hole?" Each
  of its three answers is captured as a requirement with an AC: the kept pre-commit secret
  scan and the named pre-push removal (R4: "a new project's pre-commit refuses a planted
  secret ... the release notes and `/odeo:new-project` name the push guard as no longer
  installed"), the package scan (R7: "a planted e-mail address or key produces a warning
  the user must answer"), and stale hooks (R8: "the session-start check names that hook
  and the one command that refreshes it"). R6 also keeps the repo-only tools out of the
  published tree ("the published tree contains none of them").
